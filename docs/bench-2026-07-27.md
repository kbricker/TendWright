## Read this first — three things behave differently than last time

1. **`jog` now refuses moves that would collide.** It checks the digital
   twin before anything reaches the servo, and a refused step leaves the
   joint exactly where it was. It will tell you which two links would
   touch. `--force` overrides it (logged to stderr), which is there on
   purpose because exploring near a limit is what jog is *for*.
2. **`teach replay` now pre-flights the whole recording** before the
   confirm prompt, including the approach to frame 0 — a move nobody
   ever recorded, computed from wherever the arm happens to be sitting.
3. **A stale `calibrate capture` from 07-23 was holding the serial
   port.** It's killed. If a tool says the port is busy, check for
   leftovers before assuming hardware.

Also worth knowing: the adapter enumerated as **`/dev/ttyACM2`** on
07-27, not `ttyACM0`. An earlier version of this line said the index "has
been climbing with each re-plug" — **that was a guess dressed as an
observation**, and it is corrected here. One reading is not a trend.

Two explanations fit, and we have not distinguished them:

- **A stale holder.** `cdc_acm` hands out minor numbers from a bitmap,
  lowest free first, and does *not* release one while a process still has
  the tty open. Unplug with something holding `ttyACM0` and the next plug
  lands on `ttyACM1`. Item 3 above is exactly that condition — a
  `calibrate capture` had been holding the port since 07-23.
- **Company on the bus.** The Pico bridge is *also* a CDC-ACM device and
  shares the `ttyACM` namespace. If it is plugged in, the servo adapter
  cannot be `ACM0` and nothing has drifted at all.

**None of this breaks auto-detect**, which is worth stating plainly so
nobody chases it: `resolve_port` globs `/dev/ttyACM*` and takes the
device if it is the only one, whatever its number. A high index is
cosmetic.

**The real hazard is the opposite case, and it is live.** If exactly one
CDC-ACM device is present and it is the *wrong* one — servo adapter
unplugged, Pico bridge still connected — the tools will open the Pico and
start writing Feetech packets at the microcontroller running the nest
firmware. Auto-detect trusts cardinality, not identity. That is #638, and
it is a Linux problem as much as a Windows one.

Until it is fixed: **pass `--port` explicitly whenever both devices could
be connected.** Leaving the USB permanently connected is still worth
doing — it avoids the whole question — but for tidiness, not safety.

## Safety

- **The power switch is the hard e-stop.** Any keypress during the
  routine is the soft one.
- Servos hold their last command while bus power is on. To make the arm
  safe to handle, **cut power** — do not rely on a tool having exited.
- The collision gate models **the arm and the table only**. The bench,
  fixtures, anything in the gripper, and the cable are all invisible to
  it. A clear verdict means *"it won't hit itself"*, never *"safe"*.
- Workspace clear and gripper empty for Phases 1 and 2.
- **The control cable no longer crosses the work area** (re-cabled
  2026-07-27, longer lead). That was a real snag risk on the previous
  runs and it is now gone — but check it anyway before the first move,
  since the new routing has never seen the arm sweep.

## Phase 1 — plug in, one attended run (~10 min)

**This is the only part that needs you watching.** Power on the bus,
then:

```bash
uv run python -m hardware.bench.scan          # all six answer?
uv run python -m hardware.bench.exercise --trace runs/baseline.csv
```

It pre-flights, prints the plan, and waits for `y`. Watch for:

- **wake with no lurch** — torque comes on against the *present*
  position, so nothing should snap
- **smooth ramp to rest**, then joints sweeping one at a time
- **the clearance opening before the m2 sweep** — m3 and m4 open to 90°
  first, and the tool refuses to sweep until the encoders confirm they
  actually did
- **ends at rest, torque off**

### The line to watch

At the end it prints something like:

```
strain: peak load 34% on joint 2, hottest 41 C on joint 3
```

**That line is the whole point of this run.** The strain guard trips at
55% sustained (3 consecutive samples), 80% instantaneous, 55 °C, or
below 6.0 V. Nobody has ever seen what a *healthy* routine actually
draws, so this run establishes it.

Two outcomes are both useful:

- **A number** — good. Now we know the headroom, and whether 55% is
  sensible or wildly off.
- **`strain: no readable health data ... strain did NOT gate this run`**
  — also fine, and important. It means the status registers don't return
  plausible values on these servos, and the guard says so out loud
  instead of pretending. Tell me and I'll rework it.

Stop the run if load climbs past ~60% and stays there, or if any joint
gets hot to the touch.

## Phase 2 — the j4 sweep, unattended (~40 min)

j4 overhauls under gravity: measured at **1594 ticks/s against a
commanded 200** — about 8× — accelerating the whole way down. Every
other joint tracks 1.1–1.6×. Acceleration is the cheapest lever we have
on it, and this sweep finds out whether it works.

Preview first, it moves nothing:

```bash
uv run python -m hardware.bench.batch --ids 4 --accel 3,5,10,15,25,40,60 \
    --repeat 3 --out runs/j4 --dry-run
```

That should say **21 runs**. Then:

```bash
uv run python -m hardware.bench.batch --ids 4 --accel 3,5,10,15,25,40,60 \
    --repeat 3 --out runs/j4
```

It stops on the first non-zero exit, health-checks between runs, and
rewrites the manifest after every one — so killing it partway still
leaves usable data. **You don't need to watch this**, but leave a hand
near the switch for the first run or two until the acceleration extremes
look sane (accel 3 is very slow, 60 is abrupt).

Then, on either machine — but **from the repo root**, since the repo is
run in place and `python -m sim.trace` needs it on `sys.path`. (The
trace file itself can live anywhere.)

```bash
uv run python -m sim.trace runs/j4/traces/<any-run>.csv
```

A trace from `runner` rather than `exercise` also needs the clip it
played, which it names in its own header. Pass it when the file is not
`<clip name>.json` in the repo root:

```bash
uv run python -m sim.trace runs/<a-clip-run>.csv --clip crane-tour.json
```

## Phase 4 — the clip runner (new, optional, ~5 min)

Added after this doc was first written (#660). It's the tool that runs a
**computed** sequence — the executor a pick-and-place will call. Worth
five minutes of your attention now because everything downstream sits on
it, and its first contact with the real arm should be something you're
watching.

```bash
cd ~/TendWright && git pull
uv run python -m hardware.bench.runner selftest    # 34 checks, no hardware
uv run python -m hardware.bench.runner example > pan-wiggle.json
uv run python -m hardware.bench.runner show --clip pan-wiggle.json
```

`example` reads `calibration.json` and writes a clip anchored to **this
arm's captured rest pose**: it starts exactly at rest, pans the base
±15° with the arm still folded, and returns. Lowest-inertia move the arm
has. `show` prints the plan and gates it without touching the bus — read
that output before running anything.

Then, with the bus powered:

```bash
uv run python -m hardware.bench.runner run --clip pan-wiggle.json --trace runs/
```

What to watch for:

- **it gates twice** — once for the whole clip before the confirm
  prompt, then again per edge from the arm's actually-measured pose. The
  second one isn't belt-and-braces: settle tolerance permits up to
  ~26 mm of tool drift, and the gate's contact margin is 5 mm.
- **any key is an e-stop**, same as `exercise`.
- **it does NOT return to rest if it stops.** It halts and holds where
  it is, and tells you which edge and where. That's deliberate —
  whatever stopped it is still there and no path back was ever gated.
  Recovery is `jog`, which gates every step.
- **it ends at rest here, so torque cuts quietly.** A clip that ended
  somewhere else would warn you first and wait for Enter.

If it stops for a reason you don't expect, send me the whole stop
report — it names the edge, both poses, and the arm's measured position.

## BIOS settings (#617)

Rewritten 2026-07-28 from photographs of the actual menus, replacing a
retracted table that had been written from general desktop-BIOS
knowledge and matched nothing on this board. Kyle, at the machine:
*"literally nothing you noted in the BIOS changes settings doc for me
aligned with what I see in the BIOS screen on this PC."*

**The machine, as the BIOS reports it:** Minisforum **UM350** (BESSTAR
TECH LIMITED), AMI **Aptio Setup Utility 2.20.1274**, BIOS **AF5PL01**
built 04/06/2022, AMD Ryzen 5 3550H with Radeon Vega, **8192 MB DDR4** @
2400. Top-level menus are `Main  Advanced  Chipset  Security  Boot
Save & Exit` — there is no ACPI menu.

*(Linux reports `bios_version` as 5.14 via DMI; the BIOS itself displays
AF5PL01. Both are real, from different fields — don't be thrown by it.)*

**There is no BIOS update to install.** Minisforum publishes none for
the UM350 — their support page lists only a 2022 Linux image — the
community mirror doesn't cover this board, and `fwupd` shows no UEFI
capsule device. Any flash would be a manual EFI-shell job with no
rollback, on a board with no published release and therefore no
changelog claiming it fixes anything. Not worth the risk of bricking the
box that runs the cell.

### Advanced → PowerManagement Configuration

Three items, and **two were already correct before anyone touched
them:**

| item | value | |
|---|---|---|
| AC Failure Resume | `[Always On]` | ✅ already right — makes a switched outlet a working power path for a hung box |
| **Lan Wake Up From COM RI1** | `[Enabled]` | ✅ already right — **this is the wake-on-LAN enable**, despite the legacy ring-indicator name |
| Wake system by RTC | `[Disabled]` | not needed |

**There is no ErP/EuP setting and no Fast Boot setting on this board.**
Both are real WoL killers on boards that have them, and both were named
in the retracted table as things to check. They do not exist here.

So **the BIOS was never why WoL didn't work** — see `hardware/cell1/`
for the actual cause (PCI PME# disabled in the OS) and the fix. Wake now
works: 26 s from cold to SSH-ready, `uv run python -m
hardware.bench.wake cell1`.

### The iGPU memory reservation — under Advanced, NOT Chipset

Corrected 2026-07-28 after Kyle searched Chipset thoroughly and found
nothing. *"I cant find anything about UMA frame buffer whatever... if
there is a setting to shift some of the ram allocation, its not in that
BIOS in an obvious place."* He was right; it had been pointed at the
wrong menu.

**It is not obvious because it does not exist as a visible item until
you change a different setting first.** The size field is hidden while
`iGPU Configuration` is on `Auto`. The path:

```
Advanced → AMD CBS → NBIO Common Options → GFX Configuration
    iGPU Configuration  →  [UMA_SPECIFIED]      ← must be set FIRST
    UMA Frame Buffer Size →  512M               ← only appears afterwards
```

`AMD CBS` is AMD's own reference-BIOS submenu, and it sits in the
Advanced list between `Network Stack Configuration` and the VLAN
entries — visible in the 2026-07-28 Advanced photograph. Options for
`iGPU Configuration` are `Auto`, `iGPU Disabled`, `UMA_SPECIFIED`,
`UMA_GAME_OPTIMIZED`. **Do not pick `iGPU Disabled`** — the bench uses
a monitor.

**Check Chipset too, and check it second.** On some AMD boards a
separate *Share Memory* item under North Bridge silently overrides the
AMD CBS value, so the size reverts after a save. Kyle describes this
board's Chipset as North Bridge / South Bridge with a few
enable/disable items, so if the AMD CBS change does not stick, that is
where to look.

⚠️ **Vendor caution, worth taking seriously here:** Minisforum's own
guidance on changing this warns it *"may cause abnormal wake-up / crash
/ not boot."* We have just spent a session making wake-on-LAN work, and
"abnormal wake-up" is precisely what we would be risking. A board that
will not POST needs a CMOS clear, which on this box means opening the
case.

**Recommendation: defer this.** It is worth ~1.5 GB (5.73 → ~7.2 GiB),
which is real but no longer urgent — the crashkernel reclaim already
landed 512 MB, and camserve's measured leak of 1.20 MB/min means
headroom buys hours, not a fix. #704 is the fix. Do this when there is
a reason to want the memory, at the machine, prepared to clear CMOS —
not as casual tidying.

### Remote shutdown — the other half of the loop

WoL gets the box **on**; this gets it **off**. Checked 2026-07-27: there
is currently **no passwordless path** — `sudo` wants a password and
polkit returns `auth_admin_keep` for `poweroff` over SSH.

Works today (the `-t` is required, or sudo cannot prompt):

```bash
ssh -t cell1 'sudo poweroff'
```

To make it scriptable — which is what the unattended workflow needs —
one sudoers drop-in, run at the bench:

```bash
sudo visudo -f /etc/sudoers.d/kyle-poweroff
```

and put exactly this in it:

```
kyle ALL=(root) NOPASSWD: /usr/sbin/poweroff, /usr/sbin/shutdown
```

Use `visudo -f`, not an editor or `tee` — it validates the syntax
before saving, and a malformed sudoers file locks you out of `sudo`
entirely. It grants passwordless rights to those two binaries and
nothing else.

Then `ssh cell1 'sudo poweroff'` works with no terminal and no
password, and the full cycle is: WoL packet → work → `sudo poweroff`.

### Wake-on-LAN — RESOLVED 2026-07-28

**It works.** Cold power-off → magic packet → SSH-ready in **26 s**,
reproduced on two consecutive cycles and persistent across reboots.

```bash
uv run python -m hardware.bench.wake cell1      # 26s
uv run python -m hardware.bench.wake status cell1
```

The first attempt failed twice over, and both failures are worth
keeping because neither was the thing the plan had been waiting on:

1. **cell1's MAC was recorded nowhere** — not in the repo, not in
   `~/.ssh/config` (IP only), and the ARP entry had aged out to zeros.
   Magic packets are addressed by **MAC**, not IP, so no packet could
   even be built. One `ip link show enp4s0` that should have been
   captured while the box was up. Now in `hosts.json`.
2. **The BIOS was never the blocker.** It was already configured
   correctly — see above. The real cause was
   `/sys/class/net/enp4s0/device/power/wakeup` reading `disabled`: the
   NIC was not permitted to assert PME#, so it could recognise a magic
   packet all day and the board would never power on. Firmware willing,
   OS refusing, neither side reporting the mismatch.

Both switches are needed and neither persists on `r8169`, so
`hardware/cell1/wol-enp4s0.service` re-arms them at every boot. Full
detail, install steps and the memory-reclaim work in
**`hardware/cell1/README.md`**.

**Lesson worth carrying:** this plan sat blocked for a week on "needs a
keyboard at POST" when the actual defect was one sysfs file readable
over an ordinary unprivileged SSH session. When a plan is blocked on
physical access, check what's readable remotely first — the blocker may
be imaginary, and it is cheap to find out.
